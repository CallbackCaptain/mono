# OmniHelper — техническая документация

> Внутренний справочник по расширению **OmniChat AutoResponder** (`omniHelper/`).
> К этому документу обращается Claude при вопросах об устройстве и поведении расширения.

## 1. Назначение

Chrome-расширение (Manifest V3), которое автоматически отвечает на входящие
обращения в веб-интерфейсе **OmniChat РТ** (`omnichat.rt.ru`). Оно работает
поверх чужого SPA-интерфейса оператора: само находит новые обращения в боковой
панели, открывает их, вставляет шаблон ответа и нажимает «Отправить» — без участия
человека.

Две основные функции:
1. **Приветствие** — на каждое новое обращение отправляется шаблон «Запрос принят в работу».
2. **Запрос дополнительного времени** — когда таймер обращения подходит к концу,
   клиенту автоматически отправляется сообщение с просьбой подождать (чтобы
   обращение не «протухло» по SLA-таймеру).

Поскольку API OmniChat недоступно напрямую, расширение действует как **робот в
браузере**: эмулирует клики мышью по DOM-элементам реального интерфейса.

## 2. Структура файлов

| Файл | Роль |
|------|------|
| `manifest.json` | Манифест MV3: permissions, host_permissions, регистрация content/background скриптов |
| `content.js` | **Ядро.** Вся логика автоответчика, внедряется на страницы omnichat.rt.ru |
| `background.js` | Service worker: установка дефолтов в storage, бейдж на иконке |
| `popup.html` | UI всплывающего окна (тумблер + индикатор статуса) |
| `popup.js` | Логика попапа: опрос статуса, переключение автоответа |
| `icons/` | Иконки 16/48/128 px (png + svg) |

## 3. Манифест (`manifest.json`)

- `manifest_version: 3`, версия расширения **5.2.0**.
- **Permissions:** `activeTab`, `storage`, `tabs`.
- **Host permissions:** `*://omnichat.rt.ru/*` и `*://*.omnichat.rt.ru/*`.
- **Content script** `content.js` внедряется на эти хосты при `document_idle`,
  только в главный фрейм (`all_frames: false`).
- **Background:** service worker `background.js`.
- **Action:** попап `popup.html`.

```
│ (тумблер)   │ ◄─────────────── │  OmniChatAutoResponder    │
└─────────────┘   getStats       │  (window.omniResponder-   │
                                  │   Instance)               │
┌─────────────┐                  │                           │

│ (бейдж,     │ ◄──────────────► │  │ внедрённый в страницу│  │
│  дефолты)   │                  │  │ fetch-перехватчик    │  │
└─────────────┘                  │  └─────────────────────┘  │
                                  └──────────────────────────┘
                                            │ DOM clicks

```

Главный класс — **`OmniChatAutoResponder`** в `content.js`. Единственный экземпляр
создаётся в конце файла и публикуется как `window.omniResponderInstance`. Публичный
консольный API — `window.omniResponder` (см. §10).

### Цикл работы (`init()`)
1. `loadState()` — читает состояние из `chrome.storage.local`.
2. `injectInterceptor()` — внедряет в страницу перехватчик `fetch`.
3. `setupObserver()` — вешает `MutationObserver` на боковую панель.
4. `startPeriodicCheck()` — запускает периодический опрос каждые 2 сек.
5. `exposeAPI()` — публикует `window.omniResponder`.
6. Через 3 сек — первичная проверка `checkForAppeals()`.

## 5. Обнаружение обращений

Обращения ищутся в DOM по селектору `[data-testid="appeal-preview"]`.

### `extractAppealData(element)` — извлечение данных обращения
Определяет **ID обращения** по трёхуровневому приоритету (это критично для
дедупликации):
1. **`realId`** — реальный appealId из атрибутов элемента (`data-id` /
   `data-appeal-id` / ближайший `[data-id]`).
2. **`networkId`** — appealId из сетевого маппинга `name → appealId`, собранного
   fetch-перехватчиком (`knownAppealIds`). Берётся первый ещё не обработанный ID
   для этого имени.
3. **`nameId`** — запасной вариант: ID, построенный из имени клиента
   (нормализованное имя, до 50 символов). Помечается флагом `isNameBased: true`.

> ⚠️ `nameId` нестабилен: два клиента с одинаковым именем дадут коллизию.
> Поэтому реальный/сетевой ID предпочтительнее.

### `isNewAppeal(element)` — фильтр «новизны»
Обращение считается новым, если есть бейдж `[data-testid="badge"]` или `[data-testid="dot"]`,
либо класс содержит `unread`/`new`.

### `findAppealsInSidebar()`
Собирает все новые обращения. Для name-based ID при нескольких обращениях от
одного клиента **первое сохраняет «голый» ID**, а последующие получают суффикс
`_slot_2`, `_slot_3`… (нумерация по порядку в DOM, номер слота запоминается в
`slotIndex`). Раньше суффикс получало и первое обращение (`_slot_1`) — из-за
этого уже обработанное обращение «переименовывалось», выглядело новым и клиент
получал приветствие повторно, как только появлялось второе обращение с тем же
именем.

### `getBadgeTimer(element)`
Читает число секунд из текста бейджа `[data-testid="badge"] span`. Используется
и для определения «свежести» повторных обращений, и для логики доп. времени.

## 6. Дедупликация (`shouldProcess` / `processedAppeals`)

`processedAppeals` — `Map<appealId, timestamp>`. Обращение **не** обрабатывается, если:
- нет `appealId`;
- уже в `processedAppeals`;
- уже в очереди `appealQueue`;
- сейчас обрабатывается (`currentAppealId`).

**Cooldown** = 2 часа (`cooldownPeriod`). Записи старше отбрасываются при загрузке
и при сохранении (хранится максимум 100 последних). Сохраняется в `chrome.storage.local`
под ключом `processedAppeals`.

### Повторные обращения (`checkForAppeals`)
Если обращение уже обработано, но прошло >2 мин **и** badge-таймер ≤ 60 сек
(значит, клиент написал заново), создаётся новый ID `${id}_re_${ts}` и обращение
ставится в очередь повторно с `type: 'reappeal'` и `originalId` (базовый ID).
Одновременно блокируется отправка доп. времени для этого обращения.

Защита от лавины повторов (ID с `Date.now()` уникален при каждой проверке,
а проверки идут каждые 2 сек):
- пропуск, если в очереди уже есть повтор с тем же `originalId`;
- сразу при постановке в очередь обновляется метка времени базового ID
  (`saveProcessedAppeal`), так что условие «прошло >2 мин» перестаёт выполняться
  и сканер не добавляет тот же повтор снова. Без этого, пока таймер бейджа
  оставался ≤ 60 сек, клиент получал серию одинаковых приветствий подряд.
- из-за обновлённой метки сканер не может сам повторить неудачную отправку
  re-appeal, поэтому при ошибке (`fails < maxSendRetries`) `processQueue`
  возвращает элемент в конец очереди самостоятельно.

## 7. Очередь обработки

- `appealQueue` — массив; `addToQueue()` добавляет (с проверкой `shouldProcess`).
- `processQueue()` — последовательный цикл `while` по очереди (НЕ параллельно).
  На входе guard: если `isProcessing` уже `true` — выход, второй цикл не
  запускается (два конкурирующих цикла кликали бы по разным чатам вперемешку).
  Флаг ставится/снимается только самим циклом; `clearQueue`/`clearData`
  очищают массив, но `isProcessing` не трогают — работающий цикл сам завершится
  после текущего элемента.
- Для обычного обращения после успеха вызывается `saveProcessedAppeal()` и
  сбрасывается счётчик ошибок (`failureCounts`).
- **При ошибке отправки** обращение НЕ помечается обработанным сразу: счётчик
  попыток `failureCounts` инкрементируется, и следующий `checkForAppeals()`
  поставит обращение в очередь заново (повтор). Только после `maxSendRetries`
  (3) неудач подряд бот «сдаётся»: пишет громкий лог и помечает обработанным,
  чтобы не зациклиться. Это убирает прежнее поведение, когда сломанный селектор
  молча помечал обращение обработанным без единого ответа клиенту.
- Для `type: 'extraTime'` запись в `processedAppeals` НЕ делается (повтор и так
  управляется интервалом `extraTimeRepeatInterval`).

## 8. Отправка шаблона (`sendTemplate`)

Самая хрупкая часть — она зависит от вёрстки чужого SPA. Шаги:

1. **`flushCurrentInput()`** — если в текущем поле ввода есть текст, отправляет
   его перед переключением чата. **НО** не трогает поле, если им сейчас занят
   живой оператор: пропуск, если поле в фокусе (`document.activeElement`) или с
   момента последнего «настоящего» нажатия клавиши (`event.isTrusted`, см.
   `setupOperatorTracking`) прошло меньше `operatorIdleMs` (8 сек). Так бот не
   отправит недопечатанный оператором текст. Собственные синтетические события
   бота не `isTrusted`, поэтому в детектор не попадают.
2. **Поиск элемента и клик по обращению** — `simulateClick` по элементу. Если
   элемент откреплён от DOM, повторно ищет его по имени клиента **с учётом
   `slotIndex`**: при нескольких обращениях от одного имени берётся N-й
   совпавший элемент, а не первый (иначе оба «слота» кликали один и тот же чат
   и он получал приветствие дважды).
3. **Защита от дублей по превью** (кроме `extraTime`) — превью обращения в
   сайдбаре показывает последнее сообщение чата; если там уже текст шаблона
   (целиком или первые 25 символов) — пропуск. Этот рубеж не зависит от
   селектора сообщений чата и ловит ровно «то же сообщение два раза подряд».
   Для `extraTime` не применяется: его повторы намеренные (сбрасывают SLA-таймер).
4. **Защита от дублей по истории чата** (только первичное приветствие, без
   `reappeal`/`extraTime`) — если текст шаблона уже есть в сообщениях чата
   (`[data-testid="message"]`, `.message-content`, `.chat-message`) — пропуск.
   Для повторного обращения старое приветствие в истории — норма, поэтому
   эта проверка для него отключена.
5. **Проверка поля ввода** — если в поле уже есть текст: свой залипший шаблон
   (после неудачной попытки) очищается через `clearInput`; любой другой текст
   считается черновиком оператора — бросается исключение и обращение уходит
   на повтор (шаблон не должен приклеиться к чужому тексту в одно сообщение).
6. **Открытие модалки шаблонов** — клик по `button[data-testid="choose-templates"]`,
   до 3 попыток найти модалку (`[data-testid="modal"]` / `[role="dialog"]` /
   по классам).
7. **Поиск шаблона** — ждёт `div[data-testid="reply-template"]`, ищет нужный через
   `findTargetTemplate()` по заголовку (`reply-title`) или тексту
   (`collapsable-text`). Если не найден — берёт первый.
8. **Клик по шаблону** — кликает по внутреннему `reply-title`/`collapsable-text`
   (лучше проходит через React-обработчики). Вставка **опрашивается** через
   `waitForInputText` (до 2,5 сек с шагом 200 мс), а не фиксированной паузой:
   раньше слепой повторный клик после ровно 1 сек успевал вставить шаблон второй
   раз, если приложение отрисовывало текст медленнее — и уходило одно сообщение
   с удвоенным текстом. Повторный клик по контейнеру — только если текст так и
   не появился. Финальная страховка: если текст всё же оказался в поле дважды —
   `clearInput` и исключение (обращение уйдёт на повтор с чистым полем).
9. **`clickSendButton()`** — ищет кнопку отправки по списку селекторов
   (`button[title="Отправить"]` и др.); если не найдена — fallback на нажатие Enter.
10. **Верификация отправки** (`verifyMessageSent`) — до `sendVerifyTimeout` (2 сек)
   подтверждает отправку по одному из двух сигналов: **(а)** текст шаблона появился
   среди сообщений чата, **или (б)** вставленный текст исчез из поля ввода (приложение
   очистило поле при отправке). Сигнал (б) не зависит от селекторов сообщений, поэтому
   неверный `chatMessages`-селектор не даёт ложного «не отправлено» → нет дублей при
   повторе. Если не подтвердилось — поле очищается (`clearInput`, чтобы залипший
   черновик не ушёл позже), бросается исключение, и обращение уходит на повтор (см. §7),
   а не помечается обработанным «на веру».

> Все селекторы вынесены в единый объект `SELECTORS` в начале `content.js` —
> это единственное место правки при редизайне OmniChat (см. §16).

### `simulateClick(el)`
Диспатчит полную цепочку событий с координатами центра элемента:
`pointerdown → mousedown → pointerup → mouseup → click`. Это нужно, чтобы React
в OmniChat распознал клик как настоящий.

## 9. Логика «дополнительного времени» (`checkExtraTime`)

Цель: не дать обращению истечь по таймеру. Для каждого `appeal-preview`:
- читается badge-таймер; если он `> extraTimeThreshold` (720 сек = 12 мин) — пропуск;
- обращение должно быть уже в `processedAppeals` (т.е. приветствие отправлено);
- с момента обработки должно пройти ≥ `extraTimeMinAge` (3 мин);
- пропуск, если в очереди есть приветствие/повтор для этого клиента;
- пропуск, если доп. время уже в очереди для этого обращения;
- **интервал повтора** `extraTimeRepeatInterval` (3 мин): нельзя слать чаще.

Если условия выполнены — в очередь добавляется задача `type: 'extraTime'` с
шаблоном «2.2 Ожидание общее» («Мне нужно немного времени…»). Время последней
отправки пишется в `extraTimeSent` (`Map<appealId, ts>`, сохраняется в storage).

> Доп. время проверяется даже когда очередь занята (см. `startPeriodicCheck`).

## 10. Сетевой перехватчик (`injectInterceptor`)

В страницу инъектится `<script>`, который оборачивает `window.fetch`:
- из URL с `appealId=(\d+)` — постит `omni-appeal-detected` (триггерит проверку);
- из ответов на `/appeal` или `/chat` — парсит JSON, извлекает пары
  `appealId ↔ clientName` (по множеству возможных имён полей) и постит
  `omni-appeal-mapping`.

Content script слушает `window.message` и заполняет `knownAppealIds`
(`Map<clientName, Set<appealId>>`). Это даёт стабильные реальные ID вместо
ненадёжных name-based ID.

> Перехватчик живёт в контексте страницы (через инъекцию тега script), а слушатель
> `message` — в изолированном контексте content script. Связь только через `postMessage`.

## 11. Наблюдатели и таймеры

- **`MutationObserver`** (`setupObserver`) — на `#scroll-box-root` / `.appeals-list`
  / `.chat-list`; при изменениях с debounce 1 сек вызывает `checkForAppeals()`.
  Если контейнер ещё не отрисован — ретрай каждые 2 сек.
- **`setInterval`** (`startPeriodicCheck`) — каждые `checkInterval` (2 сек):
  если не идёт обработка — полная `checkForAppeals()`, иначе только `checkExtraTime()`.

## 12. Конфигурация (`this.config`)

| Параметр | Значение по умолчанию | Назначение |
|----------|----------------------|------------|
| `responseDelay` | 2000 мс | Пауза между обработкой элементов очереди |
| `clickDelay` | 500 мс | Пауза после кликов |
| `checkInterval` | 2000 мс | Период опроса обращений |
| `cooldownPeriod` | 2 ч | Срок жизни записи об обработанном обращении |
| `templateText` | «Запрос принят в работу» | Текст приветствия |
| `templateTitle` | «1.1 Приветствие» | Заголовок шаблона приветствия |
| `extraTimeThreshold` | 720 сек | Слать доп. время, когда таймер ≤ 12 мин |
| `extraTimeMinAge` | 3 мин | Минимум после приветствия до доп. времени |
| `extraTimeTemplateText` | «Мне нужно немного времени…» | Текст доп. времени |
| `extraTimeTemplateTitle` | «2.2 Ожидание общее» | Заголовок шаблона доп. времени |
| `extraTimeRepeatInterval` | 3 мин | Частота повтора доп. времени |
| `maxSendRetries` | 3 | Сколько раз повторять отправку приветствия до «сдаюсь» |
| `operatorIdleMs` | 8000 мс | Окно «оператор печатает» после последнего настоящего нажатия — в нём `flushCurrentInput` не отправляет текст |
| `sendVerifyTimeout` | 2000 мс | Сколько ждать подтверждения, что сообщение появилось в чате |

Конфиг можно переопределить через `omniResponder.setConfig({...})` или сообщение
`updateTemplateConfig` — сохраняется в `chrome.storage.local.config`.

> ⓘ `background.js` на установке сидит в storage только `autoResponseEnabled` и
> пустой `processedAppeals`. Полный конфиг — единственный источник истины в
> `content.js` (`this.config`) и сохраняется оттуда при первом изменении.

## 13. Хранилище (`chrome.storage.local`)

| Ключ | Тип | Содержимое |
|------|-----|------------|
| `autoResponseEnabled` | bool | Включён ли автоответ |
| `processedAppeals` | `[{appealId, timestamp}]` | Обработанные (до 100, с TTL) |
| `extraTimeSent` | `[{id, timestamp}]` | Отправки доп. времени (до 100) |
| `config` | object | Переопределённый конфиг |

Все обращения к chrome API обёрнуты в `isChromeValid()` / try-catch — расширение
переживает «extension context invalidated» (например, при обновлении расширения
без перезагрузки страницы).

## 14. Связь popup ↔ content ↔ background

- **popup.js**: при открытии и раз в 3 сек шлёт `getStats` активной вкладке;
  по тумблеру — `toggleAutoResponse`. Если ответа нет — показывает «Не на OmniChat».
- **content.js** (`chrome.runtime.onMessage`): обрабатывает `getStats`,
  `toggleAutoResponse`, `checkAppeals`, `getQueue`, `clearQueue`, `clearData`,
  `processManual`, `updateTemplateConfig`, `testAutoResponse`.
- **background.js**: на `onInstalled` ставит дефолты; на `tabs.onUpdated` ставит
  зелёный бейдж «●» на вкладках OmniChat; на `tabs.onRemoved` чистит бейдж.

## 15. Публичный консольный API (`window.omniResponder`)

Доступен в DevTools-консоли на странице OmniChat:

| Метод | Действие |
|-------|----------|
| `getStats()` | Текущий статус (вкл/выкл, длина очереди, кол-во обработанных) |
| `toggle()` / `enable()` / `disable()` | Управление автоответом |
| `check()` | Принудительная проверка обращений |
| `processManual(appealId)` | Поставить конкретное обращение в очередь |
| `clearQueue()` | Очистить очередь |
| `clearHistory()` | Очистить историю обработанных + доп. времени |
| `getConfig()` / `setConfig({})` | Чтение/изменение конфига |
| `findAppeals()` | Список обнаруженных обращений (отладка) |
| `test()` | Тест открытия модалки шаблонов |
| `help()` | Справка по командам |

## 16. Уязвимые места и зависимости от вёрстки

Расширение жёстко завязано на DOM/`data-testid` интерфейса OmniChat. При редизайне
сломается. **Все селекторы собраны в объект `SELECTORS` в начале `content.js`** —
правьте там. Ключевые селекторы, за которыми надо следить:

- `[data-testid="appeal-preview"]` — карточка обращения;
- `[data-testid="badge"]` (+ вложенный `span`) — таймер/счётчик;
- `button[data-testid="choose-templates"]` — кнопка шаблонов;
- `[data-testid="modal"]` / `[role="dialog"]` — модалка шаблонов;
- `div[data-testid="reply-template"]`, `span[data-testid="reply-title"]`,
  `div[data-testid="collapsable-text"]` — шаблоны;
- `button[title="Отправить"]` и др. — кнопка отправки;
- `#scroll-box-root` / `.appeals-list` / `.chat-list` — контейнер для observer.

Прочие риски:
- **Name-based ID** при недоступности реального/сетевого ID → коллизии однофамильцев.
- Имена полей в сетевых ответах угаданы эвристически (`clientName`, `client_name`,
  `customer.name`, `name`) — при другом формате маппинг не соберётся.
- Тайминги (`waitForElement` до 5 сек) могут не дождаться при медленной сети.
