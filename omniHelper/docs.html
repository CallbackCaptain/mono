OmniHelper — техническая документация

Внутренний справочник по расширению OmniChat AutoResponder (omniHelper/) — Chrome-боту, который автоматически отвечает на обращения в веб-интерфейсе оператора OmniChat РТ.

v5.1.0 Manifest V3 Content Script DOM-автоматизация omnichat.rt.ru

1Назначение

Chrome-расширение (Manifest V3), которое автоматически отвечает на входящие обращения в веб-интерфейсе OmniChat РТ (omnichat.rt.ru). Оно работает поверх чужого SPA-интерфейса оператора: само находит новые обращения в боковой панели, открывает их, вставляет шаблон ответа и нажимает «Отправить» — без участия человека.

Две основные функции:

  1. Приветствие — на каждое новое обращение отправляется шаблон «1.1 Добрый день» («Добрый день! Мне потребуется до 5 минут…»).
  2. Запрос дополнительного времени — когда таймер обращения подходит к концу, клиенту автоматически отправляется сообщение с просьбой подождать (чтобы обращение не «протухло» по SLA-таймеру).

Поскольку API OmniChat недоступно напрямую, расширение действует как робот в браузере: эмулирует клики мышью по DOM-элементам реального интерфейса.

3Манифест (manifest.json)

  • manifest_version: 3, версия расширения 5.1.0.
  • Permissions: activeTab, storage, tabs.
  • Host permissions: *://omnichat.rt.ru/* и *://*.omnichat.rt.ru/*.
  • Content script content.js внедряется на эти хосты при document_idle, только в главный фрейм (all_frames: false).
  • Background: service worker background.js.
  • Action: попап popup.html.

Главный класс — OmniChatAutoResponder в content.js. Единственный экземпляр создаётся в конце файла и публикуется как window.omniResponderInstance. Публичный консольный API — window.omniResponder (см. §10).

Цикл работы (init())

  1. loadState() — читает состояние из chrome.storage.local.
  2. injectInterceptor() — внедряет в страницу перехватчик fetch.
  3. setupObserver() — вешает MutationObserver на боковую панель.
  4. startPeriodicCheck() — запускает периодический опрос каждые 2 сек.
  5. exposeAPI() — публикует window.omniResponder.
  6. Через 3 сек — первичная проверка checkForAppeals().

5Обнаружение обращений

Обращения ищутся в DOM по селектору [data-testid="appeal-preview"].

extractAppealData(element) — извлечение данных обращения

Определяет ID обращения по трёхуровневому приоритету (это критично для дедупликации):

  1. realId — реальный appealId из атрибутов элемента (data-id / data-appeal-id / ближайший [data-id]).
  2. networkId — appealId из сетевого маппинга name → appealId, собранного fetch-перехватчиком (knownAppealIds). Берётся первый ещё не обработанный ID для этого имени.
  3. nameId — запасной вариант: ID, построенный из имени клиента (нормализованное имя, до 50 символов). Помечается флагом isNameBased: true.
⚠️

nameId нестабилен: два клиента с одинаковым именем дадут коллизию. Поэтому реальный/сетевой ID предпочтительнее.

isNewAppeal(element) — фильтр «новизны»

Обращение считается новым, если есть бейдж [data-testid="badge"] или [data-testid="dot"], либо класс содержит unread/new.

findAppealsInSidebar()

Собирает все новые обращения. Для name-based ID при нескольких обращениях от одного клиента добавляет суффикс _slot_N, чтобы каждое получило уникальный ID.

getBadgeTimer(element)

Читает число секунд из текста бейджа [data-testid="badge"] span. Используется и для определения «свежести» повторных обращений, и для логики доп. времени.

6Дедупликация (shouldProcess / processedAppeals)

processedAppeals — Map<appealId, timestamp>. Обращение не обрабатывается, если:

  • нет appealId;
  • уже в processedAppeals;
  • уже в очереди appealQueue;
  • сейчас обрабатывается (currentAppealId).

Cooldown = 2 часа (cooldownPeriod). Записи старше отбрасываются при загрузке и при сохранении (хранится максимум 100 последних). Сохраняется в chrome.storage.local под ключом processedAppeals.

Повторные обращения (checkForAppeals)

Если обращение уже обработано, но прошло >2 мин и badge-таймер ≤ 60 сек (значит, клиент написал заново), создаётся новый ID ${id}_re_${ts} и обращение ставится в очередь повторно. Одновременно блокируется отправка доп. времени для этого обращения.

7Очередь обработки

  • appealQueue — массив; addToQueue() добавляет (с проверкой shouldProcess).
  • processQueue() — рекурсивно-последовательная обработка (НЕ параллельно): берёт первый элемент, ставит isProcessing = true, шлёт шаблон, ждёт responseDelay (2 сек) и переходит к следующему.
  • Для обычного обращения после успеха вызывается saveProcessedAppeal() и сбрасывается счётчик ошибок (failureCounts).
  • При ошибке отправки обращение НЕ помечается обработанным сразу: счётчик попыток failureCounts инкрементируется, и следующий checkForAppeals() поставит обращение в очередь заново (повтор). Только после maxSendRetries (3) неудач подряд бот «сдаётся»: пишет громкий лог и помечает обработанным, чтобы не зациклиться. Это убирает прежнее поведение, когда сломанный селектор молча помечал обращение обработанным без единого ответа клиенту.
  • Для type: 'extraTime' запись в processedAppeals НЕ делается (повтор и так управляется интервалом extraTimeRepeatInterval).

8Отправка шаблона (sendTemplate)

Самая хрупкая часть — она зависит от вёрстки чужого SPA. Шаги:

  1. flushCurrentInput() — если в текущем поле ввода есть текст, отправляет его перед переключением чата. НО не трогает поле, если им сейчас занят живой оператор: пропуск, если поле в фокусе (document.activeElement) или с момента последнего «настоящего» нажатия клавиши (event.isTrusted, см. setupOperatorTracking) прошло меньше operatorIdleMs (8 сек). Так бот не отправит недопечатанный оператором текст. Собственные синтетические события бота не isTrusted, поэтому в детектор не попадают.
  2. Клик по обращению — simulateClick по элементу. Если элемент откреплён от DOM, повторно ищет его по имени клиента.
  3. Защита от дублей — если текст шаблона уже есть в сообщениях чата ([data-testid="message"], .message-content, .chat-message) — пропуск.
  4. Открытие модалки шаблонов — клик по button[data-testid="choose-templates"], до 3 попыток найти модалку ([data-testid="modal"] / [role="dialog"] / по классам).
  5. Поиск шаблона — ждёт div[data-testid="reply-template"], ищет нужный через findTargetTemplate() по заголовку (reply-title) или тексту (collapsable-text). Если не найден — берёт первый.
  6. Клик по шаблону — кликает по внутреннему reply-title/collapsable-text (лучше проходит через React-обработчики). Если текст не появился в поле — повторный клик по контейнеру.
  7. clickSendButton() — ищет кнопку отправки по списку селекторов (button[title="Отправить"] и др.); если не найдена — fallback на нажатие Enter.
  8. Верификация отправки (verifyMessageSent) — до sendVerifyTimeout (2 сек) подтверждает отправку по одному из двух сигналов: (а) текст шаблона появился среди сообщений чата, или (б) вставленный текст исчез из поля ввода (приложение очистило поле при отправке). Сигнал (б) не зависит от селекторов сообщений, поэтому неверный chatMessages-селектор не даёт ложного «не отправлено» → нет дублей при повторе. Если не подтвердилось — поле очищается (clearInput, чтобы залипший черновик не ушёл позже), бросается исключение, и обращение уходит на повтор (см. §7), а не помечается обработанным «на веру».
📌

Все селекторы вынесены в единый объект SELECTORS в начале content.js — это единственное место правки при редизайне OmniChat (см. §16).

simulateClick(el)

Диспатчит полную цепочку событий с координатами центра элемента: pointerdown → mousedown → pointerup → mouseup → click. Это нужно, чтобы React в OmniChat распознал клик как настоящий.

9Логика «дополнительного времени» (checkExtraTime)

Цель: не дать обращению истечь по таймеру. Для каждого appeal-preview:

  • читается badge-таймер; если он > extraTimeThreshold (720 сек = 12 мин) — пропуск;
  • обращение должно быть уже в processedAppeals (т.е. приветствие отправлено);
  • с момента обработки должно пройти ≥ extraTimeMinAge (3 мин);
  • пропуск, если в очереди есть приветствие/повтор для этого клиента;
  • пропуск, если доп. время уже в очереди для этого обращения;
  • интервал повтора extraTimeRepeatInterval (3 мин): нельзя слать чаще.

Если условия выполнены — в очередь добавляется задача type: 'extraTime' с шаблоном «2.1 Требуется время для проверки» («Мне потребуется до 5 минут…»). Время последней отправки пишется в extraTimeSent (Map<appealId, ts>, сохраняется в storage).

💡

Доп. время проверяется даже когда очередь занята (см. startPeriodicCheck).

10Сетевой перехватчик (injectInterceptor)

В страницу инъектится <script>, который оборачивает window.fetch:

  • из URL с appealId=(\d+) — постит omni-appeal-detected (триггерит проверку);
  • из ответов на /appeal или /chat — парсит JSON, извлекает пары appealId ↔ clientName (по множеству возможных имён полей) и постит omni-appeal-mapping.

Content script слушает window.message и заполняет knownAppealIds (Map<clientName, Set<appealId>>). Это даёт стабильные реальные ID вместо ненадёжных name-based ID.

ⓘ

Перехватчик живёт в контексте страницы (через инъекцию тега script), а слушатель message — в изолированном контексте content script. Связь только через postMessage.

11Наблюдатели и таймеры

  • MutationObserver (setupObserver) — на #scroll-box-root / .appeals-list / .chat-list; при изменениях с debounce 1 сек вызывает checkForAppeals(). Если контейнер ещё не отрисован — ретрай каждые 2 сек.
  • setInterval (startPeriodicCheck) — каждые checkInterval (2 сек): если не идёт обработка — полная checkForAppeals(), иначе только checkExtraTime().

14Связь popup ↔ content ↔ background

  • popup.js: при открытии и раз в 3 сек шлёт getStats активной вкладке; по тумблеру — toggleAutoResponse. Если ответа нет — показывает «Не на OmniChat».
  • content.js (chrome.runtime.onMessage): обрабатывает getStats, toggleAutoResponse, checkAppeals, getQueue, clearQueue, clearData, processManual, updateTemplateConfig, testAutoResponse.
  • background.js: на onInstalled ставит дефолты; на tabs.onUpdated ставит зелёный бейдж «●» на вкладках OmniChat; на tabs.onRemoved чистит бейдж.

16Уязвимые места и зависимости от вёрстки

Расширение жёстко завязано на DOM/data-testid интерфейса OmniChat. При редизайне сломается. Все селекторы собраны в объект SELECTORS в начале content.js — правьте там. Ключевые селекторы, за которыми надо следить:

  • [data-testid="appeal-preview"] — карточка обращения;
  • [data-testid="badge"] (+ вложенный span) — таймер/счётчик;
  • button[data-testid="choose-templates"] — кнопка шаблонов;
  • [data-testid="modal"] / [role="dialog"] — модалка шаблонов;
  • div[data-testid="reply-template"], span[data-testid="reply-title"], div[data-testid="collapsable-text"] — шаблоны;
  • button[title="Отправить"] и др. — кнопка отправки;
  • #scroll-box-root / .appeals-list / .chat-list — контейнер для observer.

Прочие риски:

⚠️

Name-based ID при недоступности реального/сетевого ID → коллизии однофамильцев.

Имена полей в сетевых ответах угаданы эвристически (clientName, client_name, customer.name, name) — при другом формате маппинг не соберётся.

Тайминги (waitForElement до 5 сек) могут не дождаться при медленной сети.
